Multi-camera drone tracking

TU Delft project
  • multi-view geometry
  • triangulation
  • real-time

Problem: to monitor a drone, you need to know where it is in 3D, many times per second. One camera cannot do this: it sees the direction to the drone but not how far away it is.

What I built: a tracker that uses several calibrated cameras. Each camera finds the drone in its image, and the lines of sight from all cameras are intersected to get one 3D position per frame. With three or more cameras, one can be blocked and the tracking keeps working.

Try it: go through steps 1 to 4. Drag the room to look around. The bottom row shows what each camera sees.

What to notice: one camera gives no position at all; two give one; a third lowers the average error shown in the corner; and the pillar only stops tracking when fewer than two cameras still see the drone.

forkpoint: visual model surgery

Code ↗
  • PyTorch
  • FastAPI
  • React
  • TypeScript
  • pruning

Problem: to run an AI model on a phone or a drone, you usually have to make it smaller, which means deciding which parts to remove. But a model is millions of numbers hidden in code. You cannot see where its size is, which parts matter, or what an edit changed. So people guess, edit code, rerun scripts and compare printed numbers.

What I built: forkpoint, which turns this into something you can see and click. It draws a PyTorch model as blocks sized by their number of weights, so you see at a glance where the bulk is. You cut blocks or weights in a copy of the model (a "fork"), then run the original and the fork side by side on the same image to see which answers changed and where in the network the change started. With the model in front of you, the trade-offs become obvious: the biggest blocks are not always the ones that matter most.

Try it on a real image classifier, ResNet18, which was trained on 1000 kinds of objects and recognises all 7 of these cats. Shrink your fork with the slider, or click a block to remove it, and watch which photos stop being cats.

License plate recognition

Code ↗
  • Python
  • OpenCV
  • SVM
  • CI
  • team lead

Problem: read a car's licence plate from a car park camera, for example to open a gate or charge for parking, without any person checking it.

What I built: a TU Delft image processing project; I led the team. Our program finds the yellow Dutch plate in each video frame, cuts it into single characters, and recognises each character by comparing it with stored examples of every letter and digit (the course version also used an SVM classifier).

Try it: the program runs in your browser on real frames from the course video, with our character examples. Pick a frame and press Read the plates. Change the light and see where it breaks.

  1. Find yellow, plate-shaped regions
  2. Split each plate into characters
  3. Match characters to templates (a group between dashes is all letters or all digits)

What to notice: the close-up plates are read correctly. In the frame with two small plates, each character is only a few pixels tall: on one plate step 2 finds just one character, and on the other step 3 gets 7 of the 8 right. Below about 60% light, step 1 fails first, because the plate no longer looks yellow.

ARC-AGI with a GPT-2 trained from scratch

Code ↗
  • Python
  • PyTorch
  • GPT-2
  • data augmentation

Problem: ARC-AGI is a test of small colour-grid puzzles that people find easy and AI finds hard. Each puzzle has a new rule, and you must find it from two or three examples.

What I built: a GPT-2 style language model, trained from scratch to solve these puzzles. Each grid is written as text with 14 symbols. To get more training data, every puzzle is also rotated, mirrored and recoloured. The model learns the patterns well but often gets the size of the answer grid wrong.

Try it: find the rule from the two examples, then paint your answer and press Check. The answer does not have to be the same size as the input.

What to notice: the colours are easy, the output size is the trap. That is where my model fails most.

Camera calibration from scratch (DLT + Hartley normalisation)

Code ↗
  • Python
  • NumPy
  • camera calibration
  • optimisation

Problem: to measure anything with a camera, such as a distance, a 3D shape or a robot's position, you must know exactly how that camera turns 3D points into pixels: its focal length, position and direction. Finding these numbers is called camera calibration.

What I built: calibration from scratch in plain NumPy. The Direct Linear Transform (DLT) computes the camera from known 3D points and the pixels where they appear. Hartley normalisation rescales the numbers first so the computation stays accurate, and a final optimisation step refines the result.

Try it: a camera looks at a calibration object, and the measured points get pixel noise. Drag the image to move the camera, add noise, and switch normalisation off. Without it, the equations become about 10⁸ times more sensitive to errors (their condition number grows).
